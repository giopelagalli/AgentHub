# Daemon configs

A daemon config is the YAML file passed to `packages/node-daemon` (`tsx packages/node-daemon/src/main.ts <config.yaml>`). It tells the node daemon who it is, which hub to register with, and which model-serving processes to supervise on this machine — one entry per tier it serves. The daemon launches each `serving` entry's `cmd`, waits for it to come up on `port`, and registers the resulting endpoints with the hub so the gateway can route agent traffic to them.

`DaemonConfig` fields: `node: { name: string; arch: string }`, `hub: string`, `hubCandidates?: string[]`, `hubToken?: string` (sent as `Authorization: Bearer <token>` on every hub call; falls back to the `DAEMON_TOKEN` env var, and must match the hub's own `DAEMON_TOKEN` once the hub has `HUB_PASSWORD` set — otherwise registration is refused with a 401), `advertiseHost?: string`, `heartbeatMs?: number`, `serving?: ServingConfig[]`, `jobTypes?: JobType[]`, `workspaceRoot?: string`, `claimIntervalMs?: number`, `browser?: { enabled: boolean; port?: number; display?: string; headless?: boolean }` (the shared browser server — Mac mini only, see `deploy/macmini/README.md`). `ServingConfig` fields (one per entry in `serving`): `tier: Tier`, `model: string`, `port: number`, `maxStreams: number`, `cmd: string[]`. `serving` may be empty or omitted (it defaults to `[]`), but the daemon must declare at least one capability — a non-empty `serving`, a non-empty `jobTypes`, or `browser.enabled: true` — or `loadConfig` throws `daemon config: no capability (serving, jobTypes, browser or controlNode) declared`; a browser-only node (see `deploy/macmini/README.md`) is the main case that needs no `serving` at all. `configs/dev-node.yaml` is a working example that serves both tiers from the mock OpenAI server (`packages/mocks/src/serve.ts`) instead of a real model. Real nodes replace `cmd` with their own serving-stack launch command (e.g. a `vllm serve ...` invocation or a wrapper script around it) — everything else about the config stays the same.

### Bearer-protected endpoints (`apiKeyEnv`)

A registered `ServingEndpoint` may carry `apiKeyEnv: string` — the *name* of an environment variable the **hub** process holds. The gateway reads that variable per request and sends `Authorization: Bearer <value>`; the secret itself never travels over the registration, is never stored, and never reaches the UI. A name whose variable is unset costs one hub log line and takes that endpoint out of rotation until it is set, rather than sending an unauthenticated request. The hub's own `cloud-fireworks` node uses exactly this (`FIREWORKS_API_KEY`), and it is what a local serving stack put behind a token would use too — note that `ServingConfig` has no `apiKeyEnv` field yet, so a daemon-supervised endpoint cannot declare one without adding it there first.

### `hub` is an alias, not a machine name

Every real node's `hub` is the **tailnet alias** `http://hub.internal:4000` (an `/etc/hosts` line or a Tailscale custom DNS record pointing at whichever machine is currently the control node — `deploy/do/README.md` §6). The hub moves between the Mac mini and the Strix Halo on `/controlnode`, and pointing daemons at a machine name would strand every one of them on the machine the hub just left. Repointing the one alias record moves the whole fleet.

`hubCandidates` is the backstop for the window before the alias has moved: after three consecutive failed heartbeats the daemon re-probes `hub`, then each candidate in order, and follows the first that answers `GET /api/health` (logging the move once). List both control-node candidates' own tailnet names there. `configs/dev-node.yaml` keeps `http://127.0.0.1:4000` — there is nothing to follow on one machine.

### Control-node candidates

A node that can host the hub declares `controlNode: { hubCmd, dataRoot, hubUrl?, env? }`. `hubCmd` is the argv that starts the hub; the daemon gives it `DATA_ROOT` and the three roots derived from it, plus an allowlist of the variables the hub itself reads (`HUB_PASSWORD`, `DAEMON_TOKEN`, the Telegram pair, the external-API keys, `HUB_HOST`, `PORT`, …), resolved from `controlNode.env` first and the daemon's own environment second. Those must be set on **both** candidates: after a switch the new hub is configured entirely by what the target's daemon hands it. See `deploy/controlnode.md`.

`jobTypes` lists which `JobType`s (`'llm-session' | 'video-gen' | 'shell-task' | 'browser-lease'`) this node's job runner claims from the hub queue; omitted or empty means the node serves model tiers only and runs no job runner. `workspaceRoot` is the directory shell-task jobs run in (defaults to `<cwd>/workspace`); `claimIntervalMs` is how often the job runner polls the hub for claimable jobs (defaults to `1000`). See `configs/spark.yaml`, `configs/amd.yaml`, `configs/macbook.yaml` for real-node examples.
